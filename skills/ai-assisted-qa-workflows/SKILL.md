# AI-Assisted QA Workflows

## Overview

AI tools and agents can genuinely accelerate QA — drafting test cases in seconds, generating automation scaffolding, proposing a root cause for a flaky failure, or turning a pile of run data into a readable summary. None of that changes what makes QA work trustworthy: a human or agent still has to check it against reality before it counts as done. This skill is cross-cutting — it doesn't replace the catalog's existing skills (requirements analysis, automation patterns, flaky-test triage, test-suite quality) but sits on top of them, and it applies whenever AI is doing part of the QA work, not just when someone remembers to invoke it.

## When to Use

- An AI tool or agent is drafting test cases from a ticket, story, or acceptance criteria
- An AI tool or agent is generating or modifying Playwright/automation code
- An AI tool or agent is suggesting a root cause or a fix for an intermittently failing test
- An AI tool or agent is summarizing test results, generating a QA report, or drafting release-readiness notes
- Someone proposes merging, applying, or sharing AI-generated QA output "as-is" because it looks right or already passed once

**When NOT to use:** Using AI as a plain text editor or autocomplete for boilerplate you're independently reviewing line-by-line anyway doesn't need this skill invoked as a separate step — the review discipline below is the point, not the act of using an AI tool itself.

## Core Process

1. **Treat every AI output as a first draft, never a finished artifact.** A test case, a chunk of automation code, a root-cause explanation, or a report paragraph generated by AI starts at the same trust level as a first-pass draft from a junior engineer who has never seen this codebase before: plausible, often useful, and unverified until someone checks it against the actual system.

2. **Route AI-drafted test cases through the requirements discipline that already exists.** An AI can turn acceptance criteria into candidate test cases quickly, but it inherits every ambiguity in those criteria and will confidently fill gaps with a guess instead of flagging them. Before accepting AI-drafted test cases, run them (or the criteria they're based on) through `requirements-and-acceptance-criteria-analysis` — an AI draft does not skip that step, it just changes who typed the first version.

3. **Route AI-generated automation code through the same review bar as human-written automation.** Code that an AI generated to drive a browser or call an API is reviewed against `ui-test-automation-patterns` (locator stability, wait strategy, scoping) and `playwright-test-automation` (framework-specific conventions) exactly as if a person had written it. "It compiled and the test passed" is not review — a test can pass while asserting the wrong thing, and AI-generated assertions are not exempt from that failure mode.

4. **Never apply an AI's flaky-test root-cause or fix without reproducing and verifying it.** An AI can propose a plausible category (race condition, shared state, environment variability) and a plausible fix, but "plausible" is not "verified." Run the AI's suggested fix through the same reproduce-bisect-classify-verify protocol in `flaky-test-diagnosis-and-triage` before considering the flake resolved — the AI's explanation is an input to that process, not a substitute for it.

5. **Check AI-generated summaries and reports against the underlying data before sharing them.** A report or summary an AI produced from test-run data can misstate a pass rate, drop a failing suite, or smooth over a regression into confident-sounding prose. Before that summary goes to a stakeholder, spot-check its key claims (pass/fail counts, flagged regressions, release-readiness statements) against the actual source data it was supposed to summarize.

6. **Keep a human or accountable agent in the loop for judgment calls.** AI can generate more candidate test ideas, more draft assertions, and more prose than a person can produce in the same time — that volume is the value. It is not a substitute for the judgment step where someone decides which ideas matter, which assertions are correct, and which risks are real. Volume of output is not evidence of quality.

7. **Log where AI was used, the same way you'd log any tool-generated artifact.** A test file, fix, or report that was AI-drafted and then reviewed doesn't need a disclaimer, but if it was *not* independently reviewed, that gap should be visible (e.g., in a PR description or commit message) rather than indistinguishable from fully-reviewed work.

8. **Apply the same verify-before-trust rule to coverage-gap analysis and documentation generation.** An AI can scan a suite and a codebase and propose "you have no test for X" or draft a test plan's prose — both are useful first passes, but "AI didn't find a test for X" is not the same as "X is actually untested" (it may exist under a name or location the AI didn't correlate), and AI-drafted documentation can describe intended behavior instead of actual behavior. Confirm a claimed coverage gap by checking the suite directly, and confirm generated documentation against the real system before publishing it.

## Techniques and Patterns

### A good workflow: AI drafts, a checklist verifies

```
1. Ticket: "Add validation so checkout rejects expired promo codes."
2. AI drafts test cases from the acceptance criteria.
3. Reviewer checks the draft against requirements-and-acceptance-criteria-analysis:
   - Does every criterion have an observable pass/fail condition? (yes)
   - Are negative/edge cases covered — code expired mid-checkout, code
     expired exactly at boundary, malformed code? (AI missed the boundary
     case — added manually)
   - Any assumption the AI silently made? (it assumed a specific error
     message string — flagged and confirmed with the ticket owner instead
     of accepted as fact)
4. AI generates the Playwright test for the confirmed cases.
5. Reviewer checks the generated code against ui-test-automation-patterns:
   - Uses a stable locator, not a brittle text/CSS selector? (fixed one)
   - Waits on the actual error-toast condition, not a fixed sleep? (fixed one)
6. Test is run, passes, and only then is it merged — with the review
   itself visible in the PR (what was checked, what was fixed).
```

### A bad workflow: merged because it "looked right"

```
1. AI generates a full Playwright spec from a one-line ticket summary.
2. It runs locally and passes.
3. It's merged with no diff comment, no check against the acceptance
   criteria, no check of what the assertions actually verify.
4. Three weeks later the suite is "green" but a real regression in promo
   code handling ships anyway — the AI had asserted against its own
   guessed behavior (a specific error message it invented), and the
   guess was wrong. No test-suite-quality-review-style check ever
   caught it, because nobody looked past "it passed."
```

The difference between the two is not how the code was produced — it's whether a review step, backed by the catalog's existing skills, happened before the output was trusted.

### Flaky-test triage: AI as an input, not the verdict

```
AI suggestion: "This looks like a race condition between the payment
webhook and the UI poll — add a 2-second sleep before asserting."

Correct handling (per flaky-test-diagnosis-and-triage):
1. Reproduce at a measured rate first (e.g., 10/50 in CI).
2. Treat the AI's category guess as a hypothesis, not a diagnosis —
   bisect and confirm it actually correlates with load/timing.
3. If confirmed, prefer a proper condition-wait over the AI's proposed
   sleep (a sleep is a symptom-level fix even when the diagnosis is right).
4. Re-verify at the same reproduction rate before closing it out.

Incorrect handling: paste in the AI's suggested sleep, watch the test
pass twice, close the ticket. The fix will regress under more CI load,
and nobody re-diagnosed the actual race.
```

## Common Rationalizations

| Rationalization | Reality |
|---|---|
| "The AI wrote the test and it passed, so it must be testing the right thing" | A test passing only proves its assertions matched its own execution — if the AI guessed the wrong expected value, the test passes while verifying nothing real. Passing is not the same as correct. |
| "We don't need to review AI-generated test cases as carefully, machines don't make careless mistakes" | AI models don't make "careless" mistakes, they make confident, plausible-sounding ones — filling gaps in ambiguous criteria with an invented detail instead of flagging it. That failure mode is harder to catch than a human typo, not easier, and needs more scrutiny, not less. |
| "The AI's root-cause explanation sounds plausible, let's just apply its fix" | Plausible is not verified. `flaky-test-diagnosis-and-triage` exists precisely because intuitive-sounding explanations for flakes are wrong often enough that reproduction data, not plausibility, is the bar for closing one out. |
| "AI can replace exploratory testing entirely, it generates way more test ideas than a human" | Volume of generated ideas isn't coverage — exploratory testing's value is a human's contextual judgment about what's actually risky in this product, which an AI's generic idea list doesn't carry. Use AI to widen the candidate list, not to replace the judgment step that picks from it. |
| "It's an AI-generated report, the numbers came straight from the test run so they must be right" | An AI summarizing data can still miscount, drop a failing suite from the narrative, or round an inconvenient number into a reassuring one. The source data is authoritative; the summary is a claim about it that needs spot-checking. |

## Red Flags

- AI-generated test cases or automation code merged with no evidence anyone checked what the assertions actually verify
- An AI-suggested root cause or fix for a flaky test applied directly, with no reproduction/verification per `flaky-test-diagnosis-and-triage`
- AI-drafted interpretations of ambiguous acceptance criteria used to build tests or automation without the ambiguity being resolved with a real requirement owner
- A QA report, release-readiness summary, or test-result digest generated by AI and shared without being checked against the actual underlying run data
- A PR or ticket where "AI-generated" is treated as itself a justification for skipping review, rather than a note about provenance
- Growing reliance on AI-generated exploratory test ideas with no human judgment step narrowing them to what's actually risky

## Verification

- [ ] Every AI-generated test case was reviewed against the same quality bar as `test-suite-quality-review` (meaningful assertions, independence, behavior-describing names) before merge
- [ ] Every AI-drafted test case traces back to acceptance criteria that already passed `requirements-and-acceptance-criteria-analysis`, with any AI-introduced assumption confirmed or flagged, not silently accepted
- [ ] Every AI-generated automation change was reviewed against `ui-test-automation-patterns` and `playwright-test-automation` conventions, not merged solely because it ran and passed
- [ ] Every AI-suggested flaky-test root cause or fix was verified via the reproduce-and-verify protocol in `flaky-test-diagnosis-and-triage` before the flake was considered resolved
- [ ] AI-drafted QA report or summary content was spot-checked against the source data it summarizes before being shared
- [ ] Where AI output was used without full independent review, that gap is visibly noted (PR description, commit message) rather than indistinguishable from fully-reviewed work
